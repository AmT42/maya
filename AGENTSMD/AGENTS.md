# AGENTS.md (Repo Guide for Coding Agents)

This file is a **high-context, agent-focused guide** for working on this repo: what the app does, how it’s structured, how to run it, and the common pitfalls that previously caused wasted time.

If you are an agent picking this up in a fresh chat, read this first.

---

## 1) What this repo is

**Maya** is a document scanning app (mobile) + API backend (FastAPI).

Primary user flow:
1. User logs in / registers (JWT)
2. User scans a document on mobile (live border detection)
3. App uploads the image to backend `/upload`
4. Backend extracts metadata (OCR + LLM), stores it, and returns `extracted_info`
5. User reviews/edits the extracted info in a validation modal
6. App posts `/validate`, backend moves the file into a canonical folder structure and persists the validated info
7. User can browse documents (folder-like)
8. (Optional) semantic search and calendar event creation

There are **two operational modes**:
- **DEV mode** (`MAYA_DEV_MODE=1`): no OCR/LLM/Chroma/Calendar required; backend returns mocked extraction so mobile UX can be developed without credentials.
- **Full mode**: requires OpenRouter (Gemini) + Chroma (+ OpenAI key for embeddings) and optional Google Calendar credentials.

## 3) High-level architecture & data contracts

### 3.1 Backend API contracts (current)

Auth:
- `POST /register` (form-urlencoded): `username`, `email`, `password` → `{access_token, refresh_token}`
- `POST /login` (form-urlencoded): `username`, `password` → `{access_token, refresh_token}`
- `GET /users/me` (Bearer auth) → user object

Documents:
- `POST /upload` (multipart form-data, Bearer auth): `file` → `{doc_id, extracted_info}`
  - Stores image at `storage/<TEMP_STORAGE>/<doc_id>.jpg`
  - In full mode runs OCR + LLM + stores into Postgres + writes raw OCR chunks to Chroma
  - In DEV mode returns mocked `extracted_info` (no OCR/LLM required)
- `POST /validate` (JSON): `{doc_id, extracted_info}` → `{doc_id, validated_info}`
  - Updates the DB record fields
  - Moves image to: `storage/<user_id>/<doctype>/<expediteur>/<date>.jpg`
  - Updates `document.file_path` to the new location (important for browsing)
  - In full mode: writes JSON chunks to Chroma + creates Google Calendar event
- `GET /user/documents?path=...` (Bearer auth)
  - `path` is `/`-joined list: `doctype/expediteur`
  - Returns folder names at shallow depths, and document list at depth 2
- `GET /user/search?query=...&top_k=...` (Bearer auth)
  - Full mode: similarity search via Chroma then returns matching documents from Postgres
  - DEV mode: returns `[]`

Static files:
- Backend mounts `app/storage` as `/storage`
- Images are accessible as `http://<host>:8000/storage/<relative_path_inside_storage>`

### 3.2 File path subtleties (important)

Backend stores `Document.file_path` like:
- `storage/temp_storage/<uuid>.jpg` (temporary)
- `storage/<user_id>/<doctype>/<expediteur>/<date>.jpg` (final)

On the mobile side:
- **Never** `encodeURIComponent` the whole path (it encodes `/` and breaks routing).
- Use `mobileApp/src/utils/storageUrl.js` which uses `encodeURI` on the path and prefixes `/storage/`.

## 4) How to run (the “known good” recipes)

### 4.1 Fastest dev loop (recommended)

Goal: iPhone app runs and can scan/upload/validate without external credentials.

1) Start backend + Postgres with Docker
```bash
cd /Users/amt42/projects/maya
docker compose up -d --build
```

2) Confirm backend works on Mac:
- `http://localhost:8000/docs`

If backend fails on first boot because Postgres isn’t ready yet:
```bash
docker compose restart web
```

3) Start Metro (must be reachable by the phone):
```bash
cd mobileApp
npm start -- --host 0.0.0.0
```

4) On iPhone Safari (same Wi‑Fi as Mac), sanity checks:
- `http://<mac-ip>:8000/docs` (FastAPI)
- `http://<mac-ip>:8081/status` (Metro)

5) Run from Xcode:
- open `mobileApp/ios/mobileApp.xcworkspace`
- select your device
- set signing team + unique bundle id
- Run

6) If the phone can’t load the JS bundle:
- open RN dev menu (shake the device)
- set “Debug server host & port for device” to `<mac-ip>:8081`
- reload

### 4.2 iOS simulator

Simulator can reach `localhost` on the Mac:
```bash
cd mobileApp
npm start
npm run ios
```

### 4.3 Full pipeline mode

Requires real credentials (Vision, OpenAI, Calendar) and Chroma.

Chroma in this repo is optional and currently behind a compose profile:
- `docker compose --profile chroma up --build`

Important: `docker-compose.yml` references `../chroma` for the server service. If that directory isn’t present on your machine, do **not** enable the chroma profile until you add it.

## 5) iOS-specific pitfalls (and fixes)

### 5.1 iOS deployment target

`react-native-document-scanner-plugin` requires a higher iOS target than 12.x.
We pinned:
- `platform :ios, '13.0'` in `mobileApp/ios/Podfile`
- `IPHONEOS_DEPLOYMENT_TARGET = 13.0` in `mobileApp/ios/mobileApp.xcodeproj/project.pbxproj`

### 5.2 Flipper build failures

Flipper can fail to compile with certain Xcode/C++ toolchains (errors in FlipperKit).
We **disabled Flipper** in `mobileApp/ios/Podfile`.

If you re-enable Flipper, be prepared to fix toolchain issues (C++ standard/libc++).

### 5.3 CocoaPods “boost checksum incorrect”

Symptom:
- `Error installing boost`
- checksum mismatch

Root cause:
- the upstream URL `boostorg.jfrog.io/...` can return HTML or a different artifact.

Fixes:
1) Clean cache and reinstall:
```bash
cd mobileApp/ios
pod cache clean boost --all
pod install --repo-update
```
2) If it keeps happening, the correct tarball is available at:
`https://archives.boost.io/release/1.76.0/source/boost_1_76_0.tar.bz2`

### 5.4 iOS permissions + ATS

`mobileApp/ios/mobileApp/Info.plist` includes:
- camera usage description
- photo library usage descriptions
- local network usage description (needed for device → Mac backend)
- ATS relaxed for dev (HTTP)

## 6) Networking subtleties (mobile ↔ backend)

### 6.1 Base URL strategy (debug builds)

`mobileApp/src/config/apiConfig.js` derives the API host from the Metro bundle URL:
- if Metro host is `<mac-ip>`, API becomes `http://<mac-ip>:8000`

This is the key to making the app “just work” on a physical iPhone without hardcoding the IP in many files.

If `NativeModules.SourceCode.scriptURL` is missing (some release contexts), it falls back to:
- iOS: `http://localhost:8000`
- Android emulator: `http://10.0.2.2:8000`

**Implication:** release builds will need a real base URL configuration mechanism (e.g., in-app dev settings or build-time env).

### 6.2 Metro port conflicts

Symptom: `EADDRINUSE :::8081`

Fix:
```bash
lsof -nP -iTCP:8081 -sTCP:LISTEN
kill <PID>
```

## 7) Docker/DB subtleties

### 7.1 Postgres 18+ volume mount path

The official Postgres image changed expectations for the data directory layout.
We mount the volume at:
- `/var/lib/postgresql` (not `/var/lib/postgresql/data`)

This avoids the “configured to store database data… unused mount/volume” startup error.

### 7.2 Backend may start before DB is ready

`app/db/session.py` runs `Base.metadata.create_all(bind=engine)` at import time.
If the DB isn’t ready yet, FastAPI can crash on startup.

Quick fix:
```bash
docker compose restart web
```

Longer-term fix (future work):
- move `create_all` into a startup hook with retries or use migrations (Alembic).

## 8) Known technical debt (don’t repeat past mistakes)

- **Do not scatter backend URLs** in many files (this repo used to do that). Use `apiConfig.js` + `apiClient.js`.
- **Do not encode full file paths** with `encodeURIComponent` (breaks image URLs). Use `storageUrl.js`.
- **Avoid editing `node_modules` by hand** as a “fix”; if you must patch a dependency, automate it (Podfile hooks or upgrades).
- **Token storage** is currently AsyncStorage (not Keychain/Keystore). Treat as dev-grade.
- **Backend date types**: `Document.date` is a `DateTime` but the code sometimes passes strings; be careful if you touch date handling.
- **Unprofessional error message** exists in `app/utils/security.py` (`verify_token`); clean it if you do auth work.
